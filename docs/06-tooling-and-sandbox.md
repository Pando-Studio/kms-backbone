# Tooling and Sandbox

The backbone is a git repository and a set of conventions; everything else is tooling around it. This page covers the four pieces worth standardizing: the convention linter, utility scripts, sandboxed agent execution, and dashboards.

## Convention linter

One shell script encodes the machine-checkable rules of [conventions.md](conventions.md): date-first naming in `1.signals/` and `meetings/`, no phase directories under `3.specs/`, valid frontmatter values, no time estimates where effort sizing is required. The same script runs at every layer described in [04-knowledge-cicd.md](04-knowledge-cicd.md):

- **Agent-CLI hook** — fired after every file write by an agent, so a violation is corrected inside the agent's own working loop, before commit.
- **Git pre-commit hook** — for human contributors, same script, same rules.
- **CI job** — the authoritative run on push/PR ([`template/.github/workflows/conventions.yml`](../template/.github/workflows/conventions.yml)); local hooks are convenience, CI is enforcement.

Keeping it a single dependency-free script is deliberate: it must run identically on a laptop, inside an agent sandbox, and on a CI runner.

## Utility scripts

Small, composable scripts versioned in the repository (`scripts/`), runnable by humans and agents alike:

- **Export** — Markdown to distribution formats (docx, PDF, static HTML) for artifacts that leave the repository.
- **Indexing** — the chunk/embed/upsert pipeline of [04-knowledge-cicd.md](04-knowledge-cicd.md), callable from CI or locally for a targeted re-index (contract in [`reference/vectorization/README.md`](../reference/vectorization/README.md)).
- **Scaffolding** — create a project folder with the standard grammar, regenerate a folder index, produce a status report by scanning git history.

Scripts are knowledge too: they follow the same review path as documents.

## Sandboxed agent execution

Agents write; humans validate ([02-governance.md](02-governance.md)). For that gate to mean anything, an agent's work must be **contained until reviewed**:

- Each agent task runs in an **isolated git worktree** (same machine, separate working directory and branch) or an **isolated container** (own filesystem, repository cloned at the agent's permitted scope).
- The agent has write access only to its own branch — never to the default branch, never to another task's worktree.
- All output lands as a **pull request** and passes the standard gate: automated checks, then human validation. An agent's merge rights are zero; its blast radius is one branch.
- **Secrets never enter the sandbox scope.** Deploy keys, database credentials, and API tokens for privileged actions live only in the CI runner's secret store; the pipeline performs privileged actions *after* a human has merged. An agent that is compromised or simply wrong can propose anything and execute nothing.

Patterns and trade-offs (worktree vs container, cleanup, parallel tasks) are detailed in [`reference/sandbox/README.md`](../reference/sandbox/README.md).

## Dashboards: an optional reading layer

Everything a dashboard shows is derived from two sources that already exist: the git history and the semantic index. A dashboard is therefore a **projection, never a source of truth** — it can be rebuilt from scratch at any time, and losing it loses nothing.

Typical projections: project inventory scanned from the repository layout, phase and gate status read from frontmatter ([07-methodology.md](07-methodology.md)), activity feeds from commit history, semantic search UI over the index. Implementation is deliberately unspecified — a static site regenerated by CI is enough to start; a web app backed by a relational database synchronized on push is the richer end. The invariant is the direction of data flow: repository → dashboard, never the reverse.
